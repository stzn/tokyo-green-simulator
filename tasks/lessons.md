# Lessons

## 2026-09-18: BDDでテストを先に書く
- 指摘: 計画に「実装→テスト」の順を書いたところ、「BDDでまずテストを書いてから実装を書くこと」と修正を受けた。
- パターン: 新機能は必ず Given/When/Then 形式（Vitest、日本語）の振る舞いテストを先に書き、Red を確認してから実装する。
- 適用: 計画段階から各ステップを「テスト → Red → 実装 → Green → 整理」で書く。

## 2026-11-18: 積み上げた PR は、下の PR のマージ直後に上をマージしない
- 発見: #8（`feat/stage-export` → `feat/data-contract`）が #7 のマージの 14 秒後にマージされ、マージ先が main に切り替わる前だったため、#8 の変更が main に入らなかった。
- 対策: PR は原則 main 向けに作る。積み上げる場合は、下の PR をマージした後に上の PR のマージ先が main になっていることを確かめてからマージする。マージ後は `git log origin/main` で変更が入ったことを確かめる。

## 2026-11-18: 比喩の呼び名を使わず、何を指すかで書く
- 指摘: リポジトリやデータを「舞台」「役者」と呼んでいたところ、分かりづらいので全部消すよう求められた。
- パターン: 比喩の呼び名は、書いた側には便利でも読む側には何を指すか分からない。同じ語が別のもの（アプリとデータ）を指していると、なおさら分かりにくい。
- 適用: 地図アプリ（tokyo-green-simulator）・地点データ（stage.json）・シミュレーター（virtual-greening-sim）のように、何を指すかが分かる語で書く。新しい呼び名を作るときも同じ。
